# Document upload remediation: DOCX images and Unicode filenames

**Status:** Implemented and verified offline. A live smoke test against an approved non-production Supabase bucket and the browser is still open. See the [archived implementation plan](document-upload-image-filename-remediation.md), [parity report](../../tests/document-upload-parity-report.md), and [Unicode filename completion note](../document-upload-unicode-filename.md).

## What happens to an image

1. **Extract and associate.** The DOCX processor reads referenced embedded PNG, JPEG and GIF parts from supported body paragraphs and tables, retaining placement order. It identifies identical bytes by SHA-256, including when different relationships reference copies. Each chunk gets a list of image IDs; no storage dependency is introduced in the processor.
2. **Upload and persist.** The handler uploads the original image bytes with the raster MIME type to `docs/<storage-document-key>/images/<ingest-uuid>__imgNNN.<ext>`, with overwrite disabled. It translates IDs into object keys in `document_chunks.image_paths`. Multiple chunks can reference the same image object. Unicode document IDs use the same encoded storage root as the original. Pinecone still indexes text and does not receive image bytes or image paths. No schema migration or section JSON artifacts are needed.
3. **Retrieve and display.** Semantic search finds text chunks and hydrates every image path on the matching rows. Chat uses its existing image selection policy (threshold, cap and answer placement), so not every candidate is necessarily displayed. The browser resolves displayed paths via an authenticated `GET /api/chat/content/images/{path}` (alias `/content/images/{path}`) and uses the returned five-minute signed URL. The resolver checks the exact object and expected MIME under the validated document's `images/` prefix and returns `Cache-Control: no-store`. The web chat resolves paths again when history is loaded and retries a failed image load once with a fresh URL; it also handles image bytes when talking to the Python backend. Signed URLs are not stored in chat history.

## Association rules and deliberate differences from Python

The Python one-pixel fixture puts the image-only paragraph's PNG on the same chunk as the surrounding text. A generated Python fixture with two chunks confirms that a leading image-only paragraph and a picture in the first text paragraph are associated with the first chunk; a trailing picture after the second paragraph goes on the second chunk. Python preserves duplicate references in its per-chunk list.

.NET preserves its existing section and text splitting. As in Python, a paragraph or table contributes text first and then its images. An image goes on the chunk containing the end of that text; if the block has no text, it goes on the preceding text chunk or, at the start of a section, the first text chunk. A nonempty heading's pictures go to the new section's first text chunk. Unlike Python, .NET does not create empty-text chunks or change text chunk boundaries at an image. It rejects a section containing images but no searchable text, and it records each image path at most once per chunk. The path differs from Python's document-slug filename so rollback can safely target an individual upload attempt.

## Failure handling and scope

- Images are created before chunk rows, vectors and the original. A failed or canceled ingest compensates attempted image keys (including lost-response cases), attempted vectors, and attempted rows. Confirmed image create conflicts are excluded from cleanup. Cleanup errors surface as reconciliation failures. Document deletion removes image objects along with the rest of the document's storage tree.
- The existing original-object overwrite behavior and duplicate preflight are unchanged. An ambiguous original write can still leave or replace the shared original; the handler does not blindly delete it. Concurrent same-ID uploads, the dev route (which bypasses duplicate preflight), and upload/delete races are not transactions. No backfill is performed for documents previously ingested by .NET.
- Image extraction is limited to recognized embedded pictures in top-level body paragraphs and tables, including DrawingML inline/anchored references and VML relationship references. Headers, footers, other package stories and arbitrary OOXML layouts are not covered. Legacy DOC conversion, PDF, EML, Markdown and TXT remain text-only for images. The resolver does not migrate legacy local `images/{filename}` paths or serve existing objects with unsupported MIME metadata.
- For recognized pictures, external/invalid relationships, unsafe paths, unsupported types (including SVG), invalid image envelopes and oversized parts fail processing rather than publishing a partial result. The processor checks declared MIME and the raster envelope, not a full decode of every pixel. The DOCX limits are 512 references, 128 referenced parts, 8 MiB per image, 32 MiB aggregate extracted image bytes (including copies from distinct parts), 16 MiB document XML and 1 MiB each for relationship and content-type XML. These are in addition to the upload limit.

## Verification and rollout

- `dotnet test dotnet/CFC.ChatAI.slnx --no-restore`: 225 passed; 3 fixture-dependent tests skipped. Coverage includes association across chunks and sections, byte/MIME/path persistence, deletion, lost responses, cancellation, cleanup failure, prior-object protection, row hydration and authorized signed-link resolution.
- Python parity tests: 23 passed. The isolated two-run [upload parity report](../../tests/document-upload-parity-report.md) verifies identical PNG bytes (68 bytes with the same SHA-256), correct chunk-to-object references on both sides, and both endpoints accepting `Café Guide V2.EML` as `café-guide-v2`. Remaining `DIFFERENT` entries reflect intentional naming/order/section/response differences and capture limitations, not failure of those targeted assertions. The parity transports return canned responses; C# Pinecone is captured at the application seam.
- The changed web scripts pass JSX transpilation/parsing. Browser display, link refresh/expiry and actual provider behavior were not exercised live.
- **Live smoke test:** With approved test credentials and a private document bucket, upload the embedded-image fixture (also under a unique Unicode filename), check stored bytes/MIME and persisted image paths, run a query that selects the matching chunk, and verify the browser displays the image in both the new answer and reloaded history. Verify the signed link expires, unauthenticated callers cannot resolve it, and deleting the test document removes its original and images. Do not use production credentials for this check.
