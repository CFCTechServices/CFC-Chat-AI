# Plan: host and route the system without the Python backend

**Status: development deployment path implemented in the repository; IIS/ARR and live provider checks are pending.** Use the [.NET/IIS checklist](../../../deployment/DOTNET-IIS.md), [route inventory](routing-and-hosting-routes.md) and [recorded development defaults](routing-and-hosting-preflight.md). The original design and release gates below are retained for reference; the checklist governs the current development deployment. This does not close the [API cutover](internal-api-cutover.md), [profile security](supabase-profile-self-service-security.md), or provider acceptance gates.

## Goal and current state

The .NET site serves Blazor at the site root through IIS's ASP.NET Core Module with WebSockets. Blazor calls the separately managed API on loopback. IIS/ARR retains the approved public API method/path pairs and has no fallback to Python. The legacy `deploy-windows.ps1` and `deployment/legacy-python-iis-web.config` remain separate. The plan below records original rollout requirements; use the IIS checklist for live commands and layout.

## Decisions and prerequisites

- [ ] Inventory the actual IIS site, bindings, certificate, deployed UI revision/layout, ARR/rewrite rules, service names, ports, secrets source, startup directory and service account. Capture a rollback copy of the effective IIS config, Python service configuration and matching UI release; do not assume the checked-in files match the VM. Assign deployment and security owners.
- [ ] Inventory **method and path**, not just prefixes, for the active UI, operator clients and both backend route maps. For each, record .NET support, auth, provider prerequisites, UI contract, owner and decision: route to .NET, intentionally disable/retire, or temporarily retain on Python. Include `GET /content/images/{path}` as well as `/api/chat/content/images/{path}`. Account for the unmounted/legacy clients and Python-only routes such as video upload, bulk ingest and search/ask/recommendations; do not assume all Python endpoints are retained. Verify actual active use before retiring any feature.
- [ ] Agree which temporarily unavailable features are hidden or clearly reported in the UI. Profile writes and account lifecycle/permanent deletion remain default-off until their independent gates pass; Blazor honors the API's capability flags. Video upload is deferred. A Python-free target cannot silently depend on Python for any remaining route.
- [ ] Choose the runtime strategy (.NET 10 runtime-dependent or self-contained publish), IIS web root, release directories, persistent settings/journal and staging locations, and approved secrets mechanism. Verify .NET 10 runtime/hosting prerequisites for the chosen publish and machine architecture, disk capacity, TLS bindings, outbound provider access, model/vocabulary assets and optional LibreOffice. Do not put secrets, staging or journals in the public web root or source release. Run one .NET writer for document/account workflows until distributed coordination exists.

## Implementation work

1. **Service deployment.** Add a reviewed .NET publish/deployment path alongside—not silently replacing—the existing Python script. Install/manage the API as a Windows service (for example NSSM), with an explicit executable, working directory, environment, service identity, automatic start/restart, bounded logs and documented upgrade/uninstall procedure. Provision restricted persistent `Api:AdminSettingsPath` and, if account lifecycle is enabled, `Api:AccountLifecycleJournalDirectory`; preserve them and model files across releases. Configure document roots only under trusted operator control. The host loads `.env` from its working directory; do not rely on an interactive shell's directory or copy secrets into a release artifact. Document environment variables, bucket names, namespace, embedding paths and optional flags. Do not print credentials or tokens. Leave development ingest/delete and gated features off by default.
2. **IIS routing and Blazor layout.** Preserve the legacy config and Python deployment as the rollback baseline until cutover is approved. Hand pages, static assets and the `/_blazor` hub to ANCM. Keep `/ui/` as a compatibility redirect to `/login`. Missing assets and unsupported API paths must not return HTTP 200. Route the approved `/api/*` surface and the legacy image alias as explicitly decided in the inventory to .NET, preserving method, path, query string, authorization header and response status/body. Unsupported routes must return an intentional non-success, not fall through to the SPA or a hidden Python dependency. Verify ordering, slash/case and URL-encoding behavior with IIS itself.
3. **Proxy security and limits.** Deny `/api/ingest/dev` and its descendants at the edge for every HTTP method, including alternate casing, trailing slashes and encoded/normalized forms; do not proxy either dev ingest or dev delete even on a local proxy. Keep .NET bound to loopback and restrict direct access to trusted host processes; Development and dev flags remain off on shared hosts. Set and test IIS/ARR request-size and timeout limits alongside .NET's document limit and multipart overhead. Prevent access to config, secrets, journals and staging files. Keep forwarded-header processing off on the API and verify that public auth calls share the loopback rate-limit quota, even when clients supply forwarding headers. Do not weaken authentication or expose provider credentials.
4. **Deployment mechanics.** Publish a versioned .NET release and matching UI; validate config without logging secrets, start the new service and verify it directly before changing IIS. Apply routing and UI as one coordinated release with a reversible, documented switch; avoid an interval in which the new UI uses incompatible Python upload/delete contracts. Configure backups, service monitoring, alerts, log retention and restart behavior. `/api/health` proves only host liveness; use dependency checks and authenticated synthetic flows for readiness without treating config-only Azure health as a live completion.
5. **Developer workflow and documentation.** Provide repeatable local setup with the Blazor and API projects running separately on loopback; Blazor does not proxy development API routes. Document startup, provider/model setup, configuration-dependent 404s, asset paths, smoke tests, common failures and how to stop services. Update `README.md`, deployment/runbook instructions and the route inventory after implementation; clearly distinguish local and production commands.

## Validation and release gates

Use disposable non-production Supabase/Storage and Pinecone resources for mutating tests; record the exact target and cleanup procedure. Never aim smoke writes at production by default.

- [ ] Automated/config tests exercise rule precedence, `/` and `/ui/`, static assets, SignalR negotiation, API and image alias routing, bearer headers, missing routes, methods and denial of dev routes. Verify encoded path normalization on IIS. Check that errors are not HTML success responses and no request reaches Python in the target mode.
- [ ] Start from a clean machine or documented test host: deploy, start/restart the .NET service under its service identity, reboot or simulate restart, and verify logs, persistent paths, HTTPS and IIS bindings. Test missing/incorrect provider configuration and model files: health alone must not be mistaken for full readiness.
- [ ] With Python stopped and port 8000 unavailable, browser-smoke sign-in, session/history, chat, feedback, images in new and reopened chats, upload/download/replace/delete, and authorized/unauthorized admin flows as applicable. Exercise expired signed links, disabled profile/account features, upload limits, timeout/error responses and missing assets. Verify provider rows, Storage and vectors independently after writes and deletes; use the [delivery acceptance steps](../complete/internal-api/internal-api-remaining-endpoints-delivery.md). Run profile/account security and enabled-route tests before enabling their flags. Confirm unsupported/video paths are intentionally unavailable.
- [ ] Verify IIS rejects direct and encoded dev-route attempts through the public origin; verify the API listener is not reachable externally and forwarded IPs cannot be spoofed. Check TLS, request limits, service/secret ACLs, rate limiting and logs for sensitive values. Exercise representative concurrent uploads/chat and graceful restart under expected load.
- [ ] Operator and security owners review results, route/feature inventory, provider gates, monitoring and rollback rehearsal. Record approvals and remaining deviations; a green local .NET test suite is not deployment acceptance.

## Cutover and rollback

1. Take a consistent, recoverable snapshot of the effective IIS configuration, deployed Python-compatible UI, service configuration and persistent settings; record provider/index/bucket targets and state of outstanding document/account operations. Plan a maintenance window and designate the operator who owns the switch.
2. Quiesce mutations and drain in-flight requests on both backends before changing writers. Do not run Python and .NET concurrently against the same document IDs or account workflows: the .NET locks/journal are not distributed. Deploy and verify .NET directly; switch IIS and the matching UI together, run the approved smoke checks, and monitor. Stop Python only after all retained traffic and feature decisions are confirmed; prove it can remain stopped.
3. If checks fail, stop new writes and drain requests. Restore the saved IIS rules **and matching Python-compatible UI**, then restart/verify Python as needed. Do not blindly replay or revert provider writes: inspect and reconcile partial or ambiguous document/account operations across Supabase, Storage, Pinecone and the lifecycle journal before permitting writes or retries. Verify settings and provider compatibility, auth, UI and health after rollback. Record unresolved operations and notify the owner. Rehearse this procedure in non-production before cutover.
