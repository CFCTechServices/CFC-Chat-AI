# Document upload image and filename remediation plan

**Archived implementation plan.** See the [completion note](README.md) for what shipped, test evidence, limitations, and the outstanding live smoke test. The [Unicode filename completion note](../document-upload-unicode-filename.md) covers the filename work. Findings are in the [parity decisions](../../tests/document-upload-parity-decisions.md); the [parity report](../../tests/document-upload-parity-report.md) contains the updated captures.

## Goals and boundaries

1. For DOCX documents with supported embedded images, preserve the association between each image and its relevant chunk(s), store the image, and persist its retrievable storage path in `document_chunks.image_paths`. Verify it can reach the chat/image retrieval flow.
2. Accept the tested `Café Guide V2.EML` filename safely and use a consistent document ID throughout upload, lookup and deletion. Preserve Python's `café-guide-v2` ID. New original objects use an ASCII-safe key for Supabase; lookups can fall back to an existing literal object path for the exact ID.
3. Preserve existing behavior for ordinary text-only documents, authorization, duplicate checks and failure reporting. Do not add section JSON artifact storage as part of this work.

The image baseline is the tested embedded DOCX case, not a claim of complete Python image parity for PDF, legacy DOC, EML or every DOCX feature. Inventory and explicitly document other formats/unsupported features; extend the scope separately rather than silently claiming support. Do not change embedding models or attempt Pinecone wire parity here.

## 1. Extract and associate DOCX images

- Inspect `.archive/app/services/document_processor.py` for Python's image extraction, naming, ordering and chunk-association rules, including chunks split within a section. Define the supported mapping and unresolved edge cases before coding; compare real output rather than assuming section-wide or positional semantics.
- Extend `src/CFC.ChatAI.DocumentProcessor/Contracts/DocumentProcessingResult.cs` and related chunk contracts to expose extracted image data and chunk-to-image references without coupling the processor to storage. `DocumentProcessor` is currently explicitly text-only. Retain document order and keep existing text and section/chunk behavior for image-free inputs.
- Extend DOCX parsing in `src/CFC.ChatAI.DocumentProcessor/_Internal/DocumentProcessor.cs` to resolve embedded image relationships to package parts and retain image placement, including image-only paragraphs and images mixed with text. Map references to the appropriate chunks according to the agreed rules. Support repeated references and multiple images without creating unrelated associations.
- Treat DOCX as untrusted: reject external relationships instead of fetching URLs; validate relationship targets, package paths, content types and supported image formats. Bound image count, individual and aggregate extracted bytes and decompression work, in addition to the existing upload limit; handle malformed ZIP/XML and cancellation. Define safe behavior for unsupported or malformed images and ensure errors cannot be reported as complete image ingestion silently.
- Use stable, safe object names and MIME types under `docs/{document_id}/images/`; match Python naming for covered fixtures where practical. Resolve collisions and duplicate image references deterministically. Avoid trusting client-provided paths or types. Decide and document handling of SVG or other active formats before allowing them to be served.

## 2. Persist images and coordinate failure handling

- Update `src/CFC.ChatAI.DocumentHandler/_Internal/DocumentHandler.cs`: its current `ProcessedDocument` drops image information and constructs every chunk with an empty image list. Carry image data and references through the handler, upload images to the documents storage area, and translate each chunk's references to the corresponding successfully stored object paths. Keep Pinecone metadata minimal unless an independently justified change is required; the existing retrieval path reads the chunk row.
- Plan the operation order and compensation for image upload, chunk/vector writes and original storage. A failed upload or later failure must not result in a reported successful ingest with missing image paths. Track attempted as well as confirmed writes: an error response can be ambiguous. Attempt cleanup of newly created image objects on failures and cancellation, preserve existing compensation, and report/log reconciliation requirements when cleanup fails.
- Do not blindly delete or overwrite objects from an earlier ingest or concurrent request during rollback. Design ownership/key allocation and duplicate/concurrency behavior before implementing cleanup; the dev endpoint deliberately skips the production duplicate check, and that check alone is not a transaction. Test ambiguous responses and pre-existing objects. `DeleteAsync` already traverses `docs/{id}` but must be tested with new image objects.
- Confirm the image content endpoint accepts the chosen paths, uses appropriate MIME and security controls, and that retrieval/chat receives the persisted paths. Keep image bytes out of logs and vector metadata.

## 3. Make document IDs consistent and safe for filenames

Implemented as described in the [filename completion note](../document-upload-unicode-filename.md); the bullets below describe the original design work.

- Align `CreateDocumentId` and `DocumentId.IsValid` for the tested accented filename, with a single documented normalization/validation policy used by upload preflight, processing, duplicate lookup, storage keys, download and delete routes. `DocumentId.IsValid` currently restricts IDs to ASCII, and is shared by the handler and API endpoints. Audit `ObjectKey`/prefix validation, URL encoding, database queries and any other ID consumers before expanding it.
- Preserve `café-guide-v2` for the tested input rather than transliterating it to a different ID. Define Unicode normalization and casing, allowed characters, maximum length, empty/fallback cases and collisions deliberately; Python and .NET regex/casing rules are not necessarily equivalent for all scripts. Do not silently rename already stored documents or claim universal Unicode parity. Determine how existing Python IDs, including normalization variants, are looked up without creating duplicate identities.
- Preserve rejection of traversal, separators, encoded separators, controls and unsafe route/key values. Check decoding exactly once at each boundary and test encoded and double-encoded input; keep reserved-name and filename checks unless explicitly reviewed. Specify behavior when a safe derived ID exceeds limits and ensure invalid requests cause no provider writes.
- Review duplicate-check races and slug collisions such as punctuation, case and Unicode normalization variants. Test that the authenticated route detects an existing ID and that upload, storage, retrieval, download and delete all use the same ID. Keep any migration/backfill of existing IDs as a separate, explicitly reviewed operation.

## 4. Verification and acceptance

- **Processor:** unit tests with the existing one-pixel DOCX plus generated fixtures for multiple images, repeated image references, image-only paragraphs, mixed text/image ordering, headings and chunks split around images. Assert text remains stable and references point only to the intended chunks. Exercise broken/external relationships, unsupported types, limits and cancellation. Include text-only regression tests.
- **Handler:** fake storage/chunk/vector tests assert uploaded bytes, MIME, keys and corresponding chunk `image_paths`; cover delete, failure at each write, ambiguous responses, compensation failure, pre-existing objects and cancellation. Assert no reported success with missing image data; prove neighboring documents are untouched.
- **Filename and lifecycle:** unit and API tests for the accented fixture, uppercase extension, ordinary ASCII, non-Latin examples, combining marks, casing/normalization variants, punctuation-only and long names, reserved names, separators, percent encoding and control characters. Assert duplicate behavior and end-to-end ID consistency across authenticated upload, lookup, download and delete; retain negative security tests.
- **Parity harness:** update `tests/DocumentUploadParity` with explicit assertions for the supported image and filename outcomes, not merely `DIFFERENT` counts. For the image fixture compare bytes/hash, storage path semantics and chunk references; for the filename fixture compare accepted status and derived ID. Regenerate the report and explain remaining intentional section, response and ordering differences. Its fake C# vector seam and canned provider responses remain limitations.
- **Integration:** in a non-production environment with approved test credentials and cleanup, verify actual Supabase upload, MIME, overwrite policy, chunk hydration and image endpoint/chat retrieval; test percent-encoded Unicode paths end to end. Verify provider/cleanup failures where safely possible. Unit and offline parity results alone do not prove live storage or rollback behavior.

**Done means:** the two reported cases pass the targeted automated checks, image retrieval is demonstrated in an appropriately isolated integration test, the filename is usable across the document lifecycle, and unsupported cases and residual parity gaps are documented. No claim of complete format, Pinecone SDK or real-model parity is implied.
